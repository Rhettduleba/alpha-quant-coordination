## §3 Why this matters architecturally

The bot was designed as a narrow, deterministic executor with hard criteria (`MIN_PRICE`, `MIN_VOLUME`, `MIN_NET_CHANGE_PCT`, etc.). The advisor was designed as a smart, learning layer that could ADD constraints in the right conditions. The blueprint works as long as the advisor reasons from clean data.

Today's failure pattern is:

1. Bot runs 24/7 → logs ~20k "Market closed" rejections per day.
2. Advisor's prompt feeds it the journal, including this noise.
3. Advisor (Claude Sonnet) reads "thousands of blocked entries today" and reasonably infers something is wrong with market conditions.
4. Advisor emits `BLOCK_ALL_NEW_ENTRIES` as a defensive response.
5. Bot honors it; zero trading happens that day.
6. Tomorrow's journal now contains "zero trades yesterday" alongside more out-of-hours noise.
7. Loop reinforces.

**The root cause is data contamination — the advisor cannot tell signal from noise because the bot logs both at the same level.** Fixing `BLOCK_ALL_NEW_ENTRIES` in isolation doesn't solve this. The advisor will find some other reason to over-block as long as the journal is noise-heavy.

## §4 Proposed review scope

Eight areas. Each gets investigated, findings recorded, fix proposed, then prioritized.

| # | Area | What we look for |
|---|---|---|
| R1 | **Operating-hours architecture** | Should the bot run 24/7 or only during market hours? Is `is_market_open()` actually respected, or are entries attempted in pre/post sessions? What does the watchdog do during off-hours? |
| R2 | **Journal data quality** | What is the actual signal-to-noise ratio in `trade_journal.csv`? What's the right level of logging for blocked-because-of-market-hours vs blocked-because-criteria-not-met? |
| R3 | **Advisor control vocabulary** | Of the 9 control types, which are genuinely useful vs. which are dangerous when autonomously emitted? `BLOCK_ALL_NEW_ENTRIES` is the obvious one to remove or gate behind human confirmation. |
| R4 | **Advisor prompt design** | What does the advisor's prompt actually contain? Is it asking Claude to filter journal by market hours, or feeding raw noise? `ai-trading-strategy-agent/src/advisor/prompt_builder.py`. |
| R5 | **Watchdog scheduling** | `watchdog_supervisor.py` keeps the bot alive 24/7. Should it sleep outside market hours? Trade-off: faster startup at 9:30 AM if it's already warm, vs. cleaner journal if it only runs RTH. |
| R6 | **Performance baseline integrity** | The "verified baseline" was journal-derived and wrong. Establish authoritative broker-truth baseline. Requires solving the 600-order API cap (pagination or windowed queries). |
| R7 | **Reconciliation reliability** | Already fixed 3 bugs in `daily_reconciliation.py`. Other reporting tools (`performance_summary.py`, `journal_analyzer.py`, etc.) may have similar bugs that mis-state results. |
| R8 | **Cross-checks / sanity monitoring** | Nothing currently detects "advisor emitted a globally-bad control." Need automated sanity check: if advisor emits `BLOCK_ALL_NEW_ENTRIES` or any directive that would result in <N expected trades, flag for human review before bot honors it. |

## §5 Investigation methodology

For each Rn item, one investigation pass:

1. **Read the canonical file(s)** for that area.
2. **Query supporting data** — journal CSV, log files, control history, broker API.
3. **Identify the actual current behavior** — not the documented or assumed behavior.
4. **Identify the gap** between current behavior and what makes sense.
5. **Propose fix** with effort estimate (small / medium / large) and risk level (safe / behavior-changing / risky).

All findings go into a single `SYSTEM_REVIEW_FINDINGS.md` document in this coordination repo. Rhett reviews; browser Claude weighs in; then we sequence fixes.

## §6 Fix prioritization framework

| Priority | Criterion |
|---|---|
| **P0** | Stops the bot from operating wrong right now, or removes the contamination loop. Fix before any other change. |
| **P1** | Data integrity — anything that makes downstream analytics or advisor reasoning wrong. |
| **P2** | Removes dangerous autonomous behaviors (the `BLOCK_ALL_NEW_ENTRIES` class of issue). |
| **P3** | Adds sanity checks or cross-validation that catches future regressions. |
| **P4** | Reporting / baseline / cleanup work that doesn't change bot behavior. |

Likely P0 candidates: stop the bot from logging "Market closed" rejections (or stop scanning at all outside RTH). That breaks the noise loop in one change.

## §8 Questions where browser Claude's perspective would help

These are decisions where two AI perspectives + Rhett's call is the right process:

1. **24/7 bot vs. RTH-only bot.** Should `run_bot.py` exit at 4:00 PM ET and restart at 9:00 AM, or stay alive but go quiet? Both have trade-offs. Recommend: RTH-only — simpler, cleaner journal, no fake "blocked" entries to confuse the advisor.

2. **Should `BLOCK_ALL_NEW_ENTRIES` exist as an autonomous control at all?** Today's failure shows it's dangerous when the advisor reasons from noisy data. The manual `daily_shutdown.json` kill switch already exists for human emergency stops. Recommend: remove from advisor's vocabulary, keep kill switch for humans only.

3. **Should the advisor's prompt include pre-market journal data?** Currently the journal feed to the prompt includes overnight + pre-market attempts. Filtering to RTH-only entries would remove much of the noise but loses some context. Recommend: filter to RTH for the "recent trades" signal; keep pre-market context if explicitly tagged.

4. **Should we wipe `advisor_memory.json` and rebuild from broker truth?** The advisor's accumulated memory was built from journal-derived inferences which we now know to be unreliable. Risk: starting cold loses real learned patterns. Recommend: archive current memory, restart fresh after R1-R5 fixes land.

5. **Should the V4 broker-truth baseline (297 pairs / -$2,846 / 11 days) be cited as the authoritative recent baseline, replacing the disproven "540 / -$37,614"?** Recommend: yes, with the caveat that the earlier 10 days remain unknown until pagination is added (V5).

6. **What's the right cadence for advisor runs?** Currently 3x daily (~8:00 AM, 12:30 PM, 4:30 PM). With cleaner data, would less-frequent or more-frequent runs be better? This is a downstream question for after the plumbing is fixed.

7. **Should bot launchers exist as desktop icons at all, or move to Task Scheduler?** Today's broken-launcher discovery showed Rhett wasn't actually using them. Task Scheduler-driven start at 9:00 AM, stop at 4:30 PM aligns with the RTH-only proposal.
